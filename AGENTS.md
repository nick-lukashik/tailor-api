# AGENTS.md

The API of Tailor (Work Finder), created from `nest-starter`: HTTP, config, logs, health, metrics and PostgreSQL (Drizzle). Modules: `access` (id-api access tokens through `@nick-lukashik/auth`, the `tailor` role check, `GET /me`), `applications` (the person's pool: vacancies and what was sent to them, per user), `vacancies` (shared vacancy rows found by a normalized link, the intake of pasted links and texts into the pool, the `vacancy.fetch` job that reads each link, and the `vacancy.parse` job), `llm` (the client of the platform LLM gateway), `profile` (the person's profile document: sections in jsonb columns, versions, snapshots), `master-cv` (the profile as a PDF through tailor-tex, no vacancy), `storage` (Cloudflare R2 through its S3 API), `cv-generation` (a CV tailored to each vacancy of the pool: the `cv.generate` job and the versions in `cvs`), `materials` (the texts for applying by hand from each ready CV: the `materials.generate` job and the versions in `materials`) and `cv` (the CV of an application on `cv.<domain>/<application id>/<file name>`: the newest ready version from R2, the demo PDF for the demo rows). pg-boss (jobs) is here for the fetch, parse, CV and materials jobs; Redis and RabbitMQ (events through outbox/inbox) are added only when the service uses them, copied from `nest-example` ("Add a capability" in `README.md`). The human-facing description is `README.md`.

## Commands

- `pnpm install`: dependencies (Node 26, pnpm 12; versions pinned exactly).
- `pnpm infra:up` / `pnpm infra:down` / `pnpm infra:reset`: Postgres 18 from `compose.yaml`.
- `pnpm env:local`: `.env` from `.env.example`; `pnpm db:migrate`: build and migrations; `pnpm dev`: build, `tsc --watch` and `node --watch`.
- `pnpm verify`: lint + typecheck + build + test. It must be green before you hand work over; report the command and its actual result.
- `pnpm test:unit` (no Docker), `pnpm test:int` (Testcontainers, needs Docker: Postgres and the S3 stand-in for R2, `adobe/s3mock`). Tests only through `vitest run`, never watch.
- `pnpm db:generate --name <what_it_changes>`: an SQL migration from `src/db/schema.ts`; read the generated SQL.
- `pnpm format`: Biome with fixes.

## Structure

- `src/main.ts`: entry point; `src/app.module.ts`: module wiring; `src/app.setup.ts`: HTTP setup (shared with the tests).
- `src/config/`: the Zod env schema (`env.ts`) and the `registerAs` groups (`config.ts`). Nothing else reads `process.env`.
- `src/common/`: infrastructure without business logic, identical to `nest-example` and ready to move into a package: `http` (errors, request id, cursors, validation), `database`, `health`, `metrics`, `logging`, `openapi`, `context` (AsyncLocalStorage). Change it in `nest-example` first, then copy it here.
- `src/db/`: Drizzle schema, types, `migrate.ts` (Argo CD Sync-hook Job before the Deployment: `node dist/db/migrate.js`).
- `src/access/`: `@TailorAccess()` (a valid token carrying the `tailor` role, `TAILOR_ROLE`) and `GET /me`. Every controller under `/api/v1` but `cv` is `@TailorAccess()` or `@Authenticated()`; `test/access.int.test.ts` calls every OpenAPI route without a token and expects 401.
- `src/profile/`: the profile document (`profile.schemas.ts`, strict Zod per section, cross-checks), `profiles` and `profile_snapshots`.
- `src/tex/`: the tailor-tex client (`POST /api/v1/cv/render` and `/measure`, 60 s each, errors mapped to 422/503/504) and `cv-document.ts`, copies of tailor-tex's `CvDocument` and `CvMeasurement` schemas: change both sides together.
- `src/master-cv/`: `buildMasterCv` (pure: profile → `CvDocument`, unit-tested; `cvFrame` is the header, education and languages every CV shares) and `GET /api/v1/profile/cv.pdf`.
- `src/storage/`: `ObjectStorage` (R2: put, head, get as a stream under `R2_PREFIX`; `R2_ENDPOINT`/`R2_ACCESS_KEY_ID`/`R2_SECRET_ACCESS_KEY` optional, all or none; `StorageError` with `storage_not_configured`, `storage_unavailable`, `storage_refused`). Never log bodies or keys.
- `src/cv-generation/`: the CV of an application tailored to its vacancy ("CV generation" in `README.md`). Pure and unit-tested: `analysis.ts` (grounding, the AI-role rule of D-115, role weights, quotas, ranking), `compose.ts` (the model's composition applied: cases by id, figures only from the case, exactly the quota's target, the count of bullets left unchanged), `general-cv.ts` (a general vacancy, `vacancyKind`: the master CV as is, shortened only by the fit), `skills.ts` (D-118 coverage, the vacancy's spelling, English only, one item per skill), `title.ts` (the CV title: English, senior, at most 60 characters), `tailored-cv.ts` (the `CvDocument`), `fitting.ts` (measure and shorten until `settings.maxPages`, no overfull line). `cv.prompts.ts` and `cv-generation.schemas.ts`: change them together and bump `CV_PROMPT_VERSION`; never add a rule that lets the model invent experience or write a bullet without a case. `cv-generator.ts` (the steps), `cv-generate.job.ts` (`cv.generate.<model>` queues from `LLM_CV_MODELS`, the triggers, `cv_generate_total{result,model}`), `cvs.repository.ts`, `POST /api/v1/applications/:id/cv`.
- `src/materials/`: the materials of an application ("Materials" in `README.md`): cover letter, e-mail, Telegram message, LinkedIn note, why me. `materials.ts` (pure, unit-tested: the language, the `{cvUrl}` link put in and kept whole, the limits), `materials.prompts.ts` and `materials.schemas.ts` (change together, bump `MATERIALS_PROMPT_VERSION`; facts only from the CV and the profile, style samples only as templates with `[slots]`), `form-answers.ts` (pure, unit-tested: the answers to the vacancy's `apply_form`, standard fields from the profile, the rest from the model, options checked), `materials-generate.job.ts` (`materials.generate.<model>` from `LLM_LETTERS_MODELS`, queued by the CV job when a version becomes ready, in its transaction; `materials_generate_total{result,model}`), `materials.repository.ts`, `POST /api/v1/applications/:id/materials`.
- `src/cli/`: `import-vacancies.ts` (`node dist/cli/import-vacancies.js <userId> < file.json`, the intake in chunks of 200; `importVacancies` is the tested core, `main` runs only as the entry point).
- `src/common/jobs/`: pg-boss (`PG_BOSS`, schema `pgboss`, stopped in `beforeApplicationShutdown`), a copy of nest-example's; `src/db/migrations.ts` installs its schema after the Drizzle migrations.
- `src/llm/model-pool.ts` (pure) and `model-pool.repository.ts`: a job's pool of models, one queue each (`LLM_PARSE_MODELS`, `LLM_CV_MODELS`, `LLM_LETTERS_MODELS`): the emptiest queue, a provider outage moving a job once.
- `src/llm/`: the LLM gateway client (`POST {LLM_GATEWAY_URL}/api/v1/chat/completions`, `json_schema` output checked by Zod, `reasoning_effort`, 300 s with the gateway's wait for a provider slot, `LlmCallError` with a short code: 5xx, 429, timeouts retryable, other 4xx not). Never log prompts, texts, answers or the key.
- `src/request-budget.ts`: `@RequestBudget(ms)`, a route's own request budget; every other route keeps 10 s.
- `src/vacancies/`: `vacancies` (one shared row per vacancy, `url_key` from `vacancyUrlKey`, pure and unit-tested; `parse_status` starts `pending`) and `POST /api/v1/vacancies/intake` (1–200 links and/or texts, one transaction: find or create the vacancy, then the caller's application for it, and for each new or newly filled vacancy a `vacancy.fetch` job when it has a link, else a parse job). `vacancy-fetch.job.ts` (one queue `vacancy.fetch`, `stately` per vacancy): `vacancy-fetcher.ts` reads the link (`fetch-routes.ts`: Greenhouse, Lever, Ashby, Workable APIs, else the page; `fetch-adapters.ts` and `fetch-html.ts`: pure mappers, HTML → text, JSON-LD `JobPosting`, plain-HTML form fields; `fetch-http.ts`: `safeFetch`, the SSRF guard, 15 s, 5 MB, 5 redirects; every request goes through it), stores `apply_form` (`apply-form.ts`), `fetch_status`, `fetch_error`, fills `raw_text` only when empty, then queues the parse in the same transaction when the vacancy is `pending`; `vacancy_fetch_total{result,source}`; `VACANCY_FETCH_ENABLED` (false in the test harness: no real network; `test/sites.ts` stands in for the sites through `VACANCY_FETCH_*_URL` and `VACANCY_FETCH_ALLOW_PRIVATE`); `POST /api/v1/vacancies/:id/fetch` re-reads it (202, 404 outside the caller's pool, 409 without a link). `vacancy-parse.job.ts`: the job, one queue `vacancy.parse.<model slug>` per model of `LLM_PARSE_MODELS` (`model:effort:concurrency,…`), each worked with that model's concurrency; `parse-pool.ts`: the parse queue names; the pool itself (`src/llm/model-pool.ts`): the queue with the fewest queued+active jobs, a vacancy with a live parse back to its queue (under its row lock, so never in two queues), and a provider outage (429/503) moving the job to another model once. `stately` per vacancy, other retries with backoff on the same queue; no text → `failed` `no_text`; the answer to `parsed` (plus `_meta: { model, effort, promptVersion }`), `title`, `company`, the empty company and role of its applications and version 1 of the CV of each application without one (`cv.generate`) in one transaction; `vacancy_parse_total{result,model}`; the old `vacancy.parse` queue is only drained into the pool (remove it in the next release); `parse.prompt.ts` and `parse.schemas.ts`: the prompt and the answer's schema, change them together and bump `PARSE_PROMPT_VERSION`. `POST /api/v1/vacancies/:id/parse` re-queues it (202, 404 outside the caller's pool).
- `src/applications/`: applications, schemas → repository → service → controller; the list joins `parseStatus` from `vacancies` and stays light; items carry `cvStatus` and `materialsStatus`; `PATCH /applications/:id` sets the status; get (`ApplicationDetail`) adds `vacancy` (raw text, parse status and error, `applyForm`, `fetchStatus`, `fetchError`, `model` from `parsed._meta`, `parsed` without `_meta`, checked against `parse.schemas.ts`) `cv` (the newest version's status, model and error, the link and pages of the newest ready one, `CV_PUBLIC_URL`) and `materials` (the newest version's status and error, the content of the newest ready one). `src/cv/`: the CV of an application, `cv.<domain>/<application id>/<file name>`; the newest ready version streamed from R2, the demo PDF for the demo rows (`user_id` null), else 404; the only routes reachable from the internet (`cv.<domain>`, rewritten to `/api/v1/cv/...` in gitops).
- `drizzle/`: SQL migrations and `meta/` (generated, never edited by hand).
- `test/`: integration tests and the harness (stand-ins for id-api, llm-gateway and tailor-tex: `identity.ts`, `llm-gateway.ts`, `tailor-tex.ts`; R2 is the S3 stand-in of `global-setup.ts`; `startApp({ NAME: undefined })` unsets a variable); unit tests sit next to the code (`*.test.ts`), shared fixtures in `test/fixtures/`.
- `Dockerfile`, `.github/workflows/ci.yml`: the image and CI follow the [service runtime contract](https://github.com/nick-lukashik/.github/blob/master/docs/service-contract.md) (kind **api**); see "Deploy" in `README.md`.

## Conventions

- Code style is Biome's (`biome.json`): 4 spaces, single quotes, no `;`, lines up to 120 characters, objects and arrays always expanded, operators at the start of a wrapped line, `type` over `interface`, `string[]`, kebab-case file names. Run `pnpm format` after edits.
- ESM: relative imports end in `.js`. Injectable classes are imported as values, not `import type` (DI reads `emitDecoratorMetadata`). Non-classes go through a `Symbol` token (`DB`, `PG_POOL`).
- Controllers are thin: the schema on the parameter (`@Body({ schema })`, `@Query({ schema })`), a service call. SQL lives only in `*.repository.ts`.
- The contract is described by Zod schemas in `<feature>.schemas.ts` with `.meta({ id })`; OpenAPI (`/openapi.json`) is built from them. Responses through `@ApiOkResponse({ standardSchema })`, errors through `@ApiErrors(...)`.
- Errors: `throw new AppError(code, message, details?)` or `notFound("Application")`. Codes: `VALIDATION_FAILED` 400, `UNAUTHORIZED` 401 and `FORBIDDEN` 403 (the guards of `@nick-lukashik/auth`, and `@TailorAccess()` without the `tailor` role), `NOT_FOUND` 404, `CONFLICT` 409 (a CV asked for before the parse or while one is made), `PAYLOAD_TOO_LARGE` 413, `UNPROCESSABLE` 422 (the profile does not make a CV), `RATE_LIMITED` 429 (once a rate limit is added), `INTERNAL` 500, `UNAVAILABLE` 503 (Postgres over a time budget or down: `ErrorFilter` maps it by SQLSTATE), `TIMEOUT` 504 (the request budget). Only `ErrorFilter` builds the response body; stacks, SQL and internal messages never leave the service.
- Time budgets (service contract): request 10 s, SQL statement 5 s, lock 2 s, idle in transaction 10 s, pool wait 2 s, migration lock wait 1 s (retried), body 1 MiB. They are set once (`DATABASE_TIMEOUTS`, `REQUEST_TIMEOUT_MS`, `BODY_LIMIT`); work that needs more goes to a job (pg-boss, see nest-example), not a longer budget. The one exception is the master CV PDF (65 s, `@RequestBudget`), which waits for tailor-tex's own 60 s.
- Degradation: readiness requires Postgres only. A dependency added later registers a check with `health.register(name, check, { required })`; a degradable one (Redis, RabbitMQ) uses `required: false`, is reported as `degraded`, never blocks startup, and has a metric for its degraded state.
- Migrations: compatible with the code that is running (add → switch → remove, over separate releases), forward only, no long-locking DDL mixed into a feature migration, backfills as batched jobs ("Migrations" in `README.md`).
- A new environment variable: `src/config/env.ts` → a group in `src/config/config.ts` → `.env.example`. Secrets have no `.default()`.
- Capabilities: add Redis, RabbitMQ or pg-boss only when a feature of this service needs it, by copying it from `nest-example` with its tests ("Add a capability" in `README.md`), never a stub "for later". Which one: a job for this service's own background work, an event to tell other services, a consumer with the inbox to react to theirs; not event → own job when the handler can do the work in its transaction ("Which mechanism" in nest-example's README).
- Logs: pino JSON, only `Logger` from `@nestjs/common`; the object first, a constant message. Secrets, tokens and personal data are never logged.
- Data of a person is filtered by `sub` of the token in the query (`where id = $1 and user_id = $sub`); someone else's row is a 404. Test fixtures are invented (`example.com`), never real profile data.
- Times in the API are ISO strings in UTC; ids are uuidv7 (`uuidv7()` in PostgreSQL 18, `randomUUIDv7()` in Node).
- Runtime: the app listens on `PORT` (local default 4000; the image and the cluster use 3000), metrics on `METRICS_PORT` (9464). The image runs as uid `10001` with a read-only root filesystem: write nothing outside `/tmp`.
- English everywhere: code, comments (short and rare) and docs.
- No secrets, real IPs or e-mail addresses in files (examples use `example.com`).
